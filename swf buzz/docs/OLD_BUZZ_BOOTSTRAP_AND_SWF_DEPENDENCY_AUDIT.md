# OLD BUZZ Bootstrap & SWF Buzz Dependency Audit

**READ-ONLY audit.** No source, config, `.env`, database or API was changed or created (OLD BUZZ and SWF Buzz alike); the only file written is this document. Everything below is labelled:

- **SOURCE FACT** — read directly from the OLD BUZZ (or SWF) source; file + symbol + line given.
- **RECOMMENDATION** — my proposal, based strictly on the facts.
- **OPEN DECISION** — something the source cannot decide for you.

Paths are relative to `buzz/buzz/` (OLD BUZZ) or `buzz/swf buzz/` (SWF Buzz). Line numbers are from the working tree as inspected.

---

## 1. Executive summary

**SOURCE FACT**

1. OLD BUZZ has **no "Super Admin"** concept. The word appears only as a test tag (`crates/buzz-core/src/git_perms.rs:778`). The equivalent deployment-level authority is called **Operator**.
2. An **Operator is a public key listed in the relay's process environment**, `RELAY_OPERATOR_PUBKEYS` (comma-separated 64-char hex). It is read once at startup (`crates/buzz-relay/src/config.rs:753`), never stored in the database, and cannot be changed at runtime — change the env var and restart. Empty (the default) disables community provisioning entirely (`config.rs:262-273`, `handlers/community_provisioning.rs:256-262`).
3. **The relay never generates or holds the operator's private key.** Whoever holds the private key matching a listed public key *is* the operator. `buzz-admin generate-key` (`crates/buzz-admin/src/main.rs:144`) prints a fresh keypair for bootstrapping; the relay only ever sees the public half.
4. An operator proves itself with **NIP-98 on HTTP**, not NIP-42: every `/operator/*` request must carry a signed kind-27235 event whose `u` tag equals `RELAY_OPERATOR_API_ORIGIN` + path, is replay-protected, and whose signer is in the allowlist (`api/operator.rs:60-97`). There is **no `X-Pubkey` fallback** on these endpoints (`operator.rs:87` passes `require_auth_token = true` unconditionally).
5. A **community** is a row in `communities` keyed by normalised `host`; the relay picks it from the HTTP `Host` header (`tenant.rs:71`). It is **not** created automatically for arbitrary hosts. Two creators exist: startup seeds the deployment's *own* community from `RELAY_URL` (`main.rs:342-375`), and an operator creates others with `POST /operator/communities` (`api/operator.rs:153`).
6. The **first community owner** is a `relay_members` row with `role = 'owner'`, `added_by = NULL`. It comes from `RELAY_OWNER_PUBKEY` (deployment community, at startup, `main.rs:410`, `bootstrap_owner`) or from the operator's request field `initial_owner_pubkey` (`create_only:true` → `create_community_with_owner`, `buzz-db/src/store/community.rs:398`). The operator and the owner are **different concepts and can be different keys**; an operator has no implicit membership in any community.
7. **In OLD BUZZ's hosted product the desktop app never signs operator requests.** It talks to an external control plane (`https://app.builderlab.xyz/api/goose`, `desktop/src-tauri/src/builderlab.rs:15`); that service holds the operator credential and calls the relay. The desktop only proves ownership of its Nostr key to that service (`builderlab.rs:503-520`).

**What this means for SWF Buzz.** SWF's current design (a human's own local key *is* the operator key; the SWF app signs `/operator/*` requests itself) uses the same **relay mechanism** as OLD BUZZ but a **different custody model** than OLD BUZZ's hosted product. It is valid on a relay you control; it is an OPEN DECISION for anything multi-customer (§15).

## 4. OLD BUZZ first owner assignment

**Path 1 — the deployment community (self-host).** `RELAY_OWNER_PUBKEY` (`config.rs:719-741`, malformed = startup error) → at startup `db.bootstrap_owner(community, owner)` (`main.rs:405-437`) → SQL in `relay_members.rs:381-428`:

1. `INSERT INTO relay_members (community_id, pubkey, role, added_by) VALUES (…, 'owner', NULL) ON CONFLICT … DO UPDATE SET role='owner'`
2. `UPDATE relay_members SET role='admin' WHERE community_id=$1 AND role='owner' AND pubkey <> $2` — **any other owner is demoted to admin**.

So changing `RELAY_OWNER_PUBKEY` and restarting **rotates** the deployment community's owner. With `BUZZ_REQUIRE_RELAY_MEMBERSHIP=true`, startup **refuses to run** without a valid `RELAY_OWNER_PUBKEY` and a stable `BUZZ_RELAY_PRIVATE_KEY` (`main.rs:319-337`).

**Path 2 — operator-created communities.** Operator → `POST /operator/communities` → `provision_community` (`community_provisioning.rs:249`):

- **`create_only:true`** (`:280-316`): requires `initial_owner_pubkey`; calls `create_community_with_owner` (`community.rs:398`) — **one transaction**: `INSERT INTO communities`, per-owner advisory lock, per-owner limit check, `INSERT INTO relay_members (…, 'owner', NULL)`. Existing host ⇒ `409 "community already exists"`; limit ⇒ `409 limit_reached`. Then publishes the NIP-43 roster snapshot (only when membership is required).
- **default ("legacy convergence") mode** (`:318-350`): `ensure_configured_community` then `provision_owner` = the same `bootstrap_owner` SQL, **which demotes any existing owner to admin**. So an operator-signed request *without* `create_only` can **rotate an existing community's owner** (documented at `:240-248`: "deployment-root authority, not create-only authority").

**Who may assign the first owner?** Only an operator (Path 2) or whoever controls the relay's env (Path 1). **Can the owner differ from the operator?** Yes — `initial_owner_pubkey` is an arbitrary valid pubkey. **Later ownership change:** `POST /operator/communities/transfer` (`operator.rs:358`, `transfer_ownership` `relay_members.rs:514`; previous owner becomes `member`), or Path 1 rotation. **Not** by a Nostr event: kind **9032** explicitly rejects `role = owner` (`handlers/relay_admin.rs:440`, "cannot set role to owner").

**Complete trace (SOURCE FACT):**

```
RELAY_OPERATOR_PUBKEYS (env, at boot)  ─┐
RELAY_OPERATOR_API_ORIGIN (env)        ─┤
operator signs NIP-98:                   │
  POST {ORIGIN}/operator/communities     │  api/operator.rs:60-97 (allowlist + replay)
  {host, initial_owner_pubkey, create_only:true}
        ↓                                │
create_community_with_owner  (1 tx)      │  buzz-db/src/store/community.rs:398
   communities(host)  +  relay_members(community, owner, 'owner', added_by NULL)
        ↓
owner later connects to wss://<host>  →  NIP-42 AUTH (challenge for that host)
        ↓                                  handlers/auth.rs:43+
   ban gate → (optional allowlist) → membership gate (relay_members)
        ↓
owner is a member with role 'owner'
        ↓
owner-only actions: kind 9030/9031/9032 (sender_role from relay_members), POST /api/invites
```

## 5. Operator vs Owner vs Admin vs Member

| | **Operator** | **Owner** | **Admin** | **Member** |
|---|---|---|---|---|
| Scope | **Deployment-wide** (spans tenants) | One community | One community | One community |
| Stored | Env `RELAY_OPERATOR_PUBKEYS` (provisioning). Admin console also: `relay_operators` table | `relay_members.role='owner'` | `relay_members.role='admin'` | `relay_members.role='member'` |

| Who can assign | Nobody at runtime (env) | Operator / relay-env only | Owner only | Owner or admin |
| Authenticated by | **NIP-98** signature checked against the allowlist | **NIP-42** (WS) then role from `relay_members`; NIP-98 for HTTP | same | same |

## 6. Authentication flow

**WebSocket — NIP-42** (`handlers/auth.rs:43-260`): relay sends a challenge → client returns a signed kind-22242 event with `relay` = the **tenant host** URL and the `challenge` (`api/bridge.rs:244`, `nip42_expected_relay_url`) → `verify_auth_event` (signature, `buzz-auth/src/nip42.rs:56`) → **ban gate** → optional **pubkey allowlist** (`BUZZ_PUBKEY_ALLOWLIST`, legacy) → **membership gate** `enforce_relay_membership` (`api/mod.rs:152`).

**HTTP — NIP-98** (`api/bridge.rs:83-146`): `Authorization: Nostr <base64 kind-27235>`; `u`/`method`/`payload` bound; replay-checked. **Only when `BUZZ_REQUIRE_AUTH_TOKEN=false`** does the bridge also accept a bare `X-Pubkey` header (`bridge.rs:132-143`, "Dev-mode fallback") — **for the community REST bridge only**.

## 7. Authorization flow

- **Operator endpoints:** `authorize_operator_request` (`operator.rs:60-97`): origin configured → NIP-98 verified with `require_auth_token=true` → replay → allowlist.
- **Community actions by role:** `sender_role` read from `relay_members (community_id, pubkey)` of the host-resolved tenant (`handlers/relay_admin.rs` ≈ 250-460): 9030 add (`:313`), 9031 remove (`:363`), 9032 change role (`:422`, owner only, never to owner).
- **Invites:** `POST /api/invites` requires role `owner`/`admin` (`api/invites.rs:280-302`); `POST /api/invites/claim` is membership-exempt, NIP-98, idempotent, always `member`.
- **Membership gate:** `check_relay_membership` (`api/mod.rs:80-140`): **if `require_relay_membership` is false it returns `OpenRelay` immediately — every authenticated key is admitted.** If true, `is_relay_member(community, pubkey)`; optional NIP-OA agent-via-owner.
- **Write integrity:** event signature verified (`handlers/event.rs:805,960`, `verify_event`) and `event.pubkey` must equal the authenticated pubkey (`handlers/ingest.rs:2253`, `event.rs:660`).

## 13. Security findings

**Direct answers (SOURCE FACT unless marked)**

1. **Can anyone become the first Super Admin by generating a Nostr key locally?** **No.** A key is an operator only if its public key is in the relay's `RELAY_OPERATOR_PUBKEYS` env (`operator.rs:82-93`). Generating a key changes nothing.
2. **What proves a key is the operator?** A valid **NIP-98 signature** by that key over an exact URL (`RELAY_OPERATOR_API_ORIGIN` + path), not replayed, with the signer in the env allowlist.
3. **Can anyone create a community?** No. Only an operator (relay API); no end-user endpoint exists in the relay. (Hosted product: the control plane does it after account login, with a per-owner cap of 5.)
4. **Can anyone assign themselves as owner?** Only an operator can name an owner (and may name itself); an existing owner cannot be replaced by 9032; the deployment owner is env-controlled. A *non-create-only* operator request can rotate an owner (`community_provisioning.rs:240-248, 318-350`).
5. **Does knowing another user's public key give privileges?** By itself, **no**, with one exception: on a relay with `BUZZ_REQUIRE_AUTH_TOKEN=false`, the community REST bridge trusts an `X-Pubkey` header (§6), so reads (e.g. `POST /query`) can be made *as* any known member. Writes still need a valid event signature and `event.pubkey == authenticated pubkey`.
6. **Can a public key alone authenticate?** WebSocket: no. NIP-98 endpoints (operator, invites): no — observed live `401 "missing Nostr auth"`. Community REST bridge: **yes when `BUZZ_REQUIRE_AUTH_TOKEN=false`** (observed live: `POST /query` with only `X-Pubkey` → `200`); no when `true`.
7. **What protects operator-only APIs?** NIP-98 (no header fallback), exact-origin binding, replay guard (fail-closed if Redis fails), env allowlist, and provisioning is off when the allowlist or origin is unset.
8. **What protects owner-only APIs?** NIP-42 authentication + `relay_members` role lookup for the host-resolved tenant + event signature + author==authenticated key; 9032 cannot grant owner.
9. **Minimum production configuration:** `BUZZ_REQUIRE_AUTH_TOKEN=true`, `BUZZ_REQUIRE_RELAY_MEMBERSHIP=true`, `RELAY_OWNER_PUBKEY`, stable `BUZZ_RELAY_PRIVATE_KEY`, correct `RELAY_URL`; plus `RELAY_OPERATOR_PUBKEYS` + `RELAY_OPERATOR_API_ORIGIN` if communities will be provisioned; `BUZZ_ADMIN_AUTH` not `disabled`.

**Other findings**
- **F1** Open relay = everyone is a "member" (`api/mod.rs:87-89`). Dev default; unsafe as a multi-user deployment.
- **F2** Operator authority is deployment-root: an operator can rotate any community's owner (non-`create_only`) and transfer ownership. Custody of an operator key is therefore high-value.
- **F3** Config comments are partly stale: `main.rs:315-318` says invalid `RELAY_OWNER_PUBKEY` is "stripped with a warning"; `config.rs:719-741` actually fails startup. Trust the code.
- **F4** Startup ordering: operator provisioning is off (fail closed) until both env values are set; setting only the keys logs a WARN.
- **F5** Discovery is deliberately not offered by the relay (unknown host ⇒ generic 404, `tenant.rs:61-92`) — a privacy property that constrains SWF's UX.

## 14. Required SWF configuration

**On the relay (OLD BUZZ, unchanged code):** everything in §11 "Production", specifically:
- `RELAY_OPERATOR_PUBKEYS` = the SWF operator public key(s); `RELAY_OPERATOR_API_ORIGIN` = the exact origin the SWF app will sign for (SWF derives it from `config.relayUrl` or `VITE_OPERATOR_API_ORIGIN`);

## 15. Open architecture decisions

- **D1 — Operator key custody.** OLD BUZZ hosted: the *control plane* holds the operator key; users never sign `/operator/*`. SWF now: the user's own key. Fine for a single-organisation deployment where the operator *is* the person. For "any user can request a community" it would require handing the operator key to every such user (unacceptable) or introducing a control-plane service. *Decision needed:* single-org (keep) vs multi-customer (control plane).
- **D2 — Identity → communities discovery (SWF limitation L1).** OLD BUZZ solves it with the control plane's account↔pubkey database. The relay alone cannot. Options: (a) relay endpoint returning hosts where the signer is a member (relay change), (b) a control-plane service, (c) keep the device address book + links.
- **D3 — Community name/description.** Relay stores neither; hosted OLD BUZZ keeps them in the control plane. Options: relay change, control plane, or keep client labels.
- **D4 — Owner rotation guard.** Whether SWF should ever expose non-`create_only` provisioning (it must not).

## 16. Recommended next steps (RECOMMENDATION)

1. **Keep as is:** NIP-98 operator calls with `create_only:true`; `initial_owner_pubkey`; kind 9030 add-member; invite mint/claim; NIP-42 in Rust; per-community membership probe; no `buzz://`; no client-side operator flag.
2. **Adapt:** none required for Phase 3.
3. **Do NOT copy:** OLD BUZZ dev conveniences (`BUZZ_REQUIRE_AUTH_TOKEN=false`, `X-Pubkey`, fixed dev keys, `BUZZ_ADMIN_AUTH=disabled`); the hosted product's Builderlab/Okta-style account layer (SWF's requirement is Okta-free); non-`create_only` provisioning.
4. **Rust / Vue / relay split:** *Rust* — key custody, all signing, NIP-42/NIP-98 event construction, egress guard (already). *Relay* — operator allowlist, community + owner creation, membership, roles, invites (all existing). *Vue* — UI only: dashboard, picker, forms; asks the relay, never decides authority.
5. **Before any production use:** set `BUZZ_REQUIRE_AUTH_TOKEN=true` and re-run the "public key alone" live test against it (this audit could not, because the local relay's launch environment was not recorded — see §17).
6. **Decide D1/D2 before promising "any user can create/see their communities" to end users.** Neither blocks chat work.

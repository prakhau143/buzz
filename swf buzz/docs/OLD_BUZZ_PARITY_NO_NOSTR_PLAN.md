# SWF Buzz — Old Buzz Parity, No-Nostr-Human-Identity Migration Plan

**Phase**: 1 (audit only). No code was modified to produce this document. Method: every claim about
current SWF Buzz source is `file:line`-cited from a direct read this pass; every claim about Old Buzz
behavior is carried from `docs/OLD_BUZZ_COMMUNITY_CHANNEL_DM_BEHAVIOR_AUDIT.md` (itself source-cited
against `../buzz`, read-only, not re-opened here). Anything not directly confirmed is marked
`UNABLE TO VERIFY FROM SOURCE`.

---

## 0. The single biggest finding — read this first

**SWF Buzz today is not "Okta plus a Nostr identity layer that can be peeled off." Nostr/pubkey
identity is not a layer — it is the load-bearing foundation of literally every mutation in the app.**
There is no HTTP backend, no session cookie, no Postgres table, and no `POST /api/*` write endpoint
anywhere in this codebase. Every one of: community roles, invites, channel membership, channel
creation, messages, threads, reactions, presence, typing, and DMs is implemented as a **signed Nostr
event published over a WebSocket to `buzz-relay`** (`docs/ARCHITECTURE.md` §4, confirmed unchanged
this pass). `useAuth.ts` (`src/features/auth/useAuth.ts:63-94`) makes this explicit: Okta only ever
produces `employeeEmail`/`applicationUserId` (the OIDC subject) for **display and audit**; the
`pubkey` that the entire rest of the app is keyed on comes from a **separate identity-resolution
step** — either a real NIP-46 bunker (`useAuth.ts:140-144`) or, in the current default path, a
**deterministic local keypair derived from the Okta `sub` via SHA-256**
(`DevSigningService.forLocalIdentity`, `src/features/signing/signingService.dev.ts:44-59`, called
from `useAuth.ts:109-113,145-147,178-179`). Either way, a Nostr keypair — not the Okta session — is
what every relay-side authorization check (`relay_members`, `channel_members`, invite claim) actually
keys on.

A grep of `src/` for `pubkey|nsec|npub|NIP-42|NIP-46|bunker|NIP-98|sign_event|SigningService` matches
**75 of the repo's ~95 TypeScript/Vue files** (§9 below has the full classification). This is not a
peripheral dependency to strip out — it is the identity model.

**Consequence for the master prompt's architecture** (`Okta → swf_session → Application User →
Community Membership → Role → Permissions`, with `POST /api/invites`, `POST /api/invites/claim`,
Postgres tables `community_invites`/`community_members`, atomic `SELECT ... FOR UPDATE` transactions):
**none of this backend exists today, in either SWF Buzz or the reference Old Buzz's `buzz-relay`
proper.** `buzz-relay` does have a real, working, transactional, hash-stored, atomic HTTP invite
system today (`OLD_BUZZ_COMMUNITY_CHANNEL_DM_BEHAVIOR_AUDIT.md` §8) — but its auth is **NIP-98
(a signed Nostr event carried as an HTTP header)**, not a cookie/session, and its authorization check
is still a `relay_members` (pubkey-keyed) row lookup, not an `okta_sub`-keyed `users`/`community_members`
table. There is currently no session-cookie-based HTTP identity system anywhere in this stack for
either app to build on.

**This means Phase 2 onward as scoped in the master prompt is not "swap an identity layer inside SWF
Buzz" — it is "stand up a brand-new backend service"** (an HTTP API + session store + Postgres schema
for `users`/`community_members`/`community_invites`, keyed by `okta_sub`) that neither SWF Buzz
(a documented "client only," `docs/ARCHITECTURE.md` line 3: "It is a **client only**: it does not
host agents, does not implement relay/DB/pub-sub logic") nor `buzz-relay` (Nostr-native, pubkey-keyed
throughout its own DB layer, `relay_members`/`channel_members`/`relay_invites`, per
`OLD_BUZZ_COMMUNITY_CHANNEL_DM_BEHAVIOR_AUDIT.md` §21) currently provide. **This is the top
architectural risk and must be resolved as an explicit decision (who owns/builds this new service,
and where it runs) before any Phase 2+ code is written** — see §10.

## 3. Recommended Phase 2+ order (reconciled against what this audit actually found)

The master prompt's Phase 2–12 assumes the invite/membership backend already exists in some form and
mostly needs a protocol swap. **That assumption doesn't hold** — §0 above establishes that a whole new
backend service (HTTP API + session + Postgres) must be built first, before any invite work can even
compile end-to-end. Recommended reordering:

1. **Decide backend ownership first (blocking everything else)** — does this new HTTP/session/DB
   service live inside `buzz-relay` (extending the existing Rust/Axum/Postgres stack, reusing its
   already-correct `community_members`/`channel_members`/role-check patterns but re-keyed to
   `okta_sub`/`users.id`), as a new sibling service, or does SWF Buzz stop being "client only"
   (`ARCHITECTURE.md` line 3) and grow its own backend? This is a team/infra decision, not something
   resolvable from source — write it into `DECISIONS.md` as a new entry before Phase 2 starts.
2. **Phase 2 (master prompt's own numbering, adjusted)**: stand up `users` table + `swf_session`
   issuance + JWKS-verified Okta callback (closes D9 at the same time). This subsumes the master
   prompt's "finalize Application User + session identity" phase but is substantially larger than
   that phase implies.
3. **Phase 3**: `community_members` table + HTTP membership endpoints, porting `permissions.ts`'s
   already-correct rule set (§1 table, row 3–4) verbatim.
4. **Phase 4–7**: invite create/claim/revoke exactly as the master prompt scopes them (§1 table rows
   6–8) — this part of the master prompt's plan is accurate as written once steps 1–3 exist.
5. **Phase 8+**: channel membership, messages, threads, DMs — each is a real new HTTP+realtime
   subsystem per §1's table, not a small delta; sequence by user-visible value (messages before
   threads before DMs, matching the master prompt's own Phase 9-11 order) but budget for this being
   the largest chunk of work in the whole migration, not a formality after invites are done.
6. **Explicitly descoped/flagged, not silently dropped**: platform-admin (Operator/Moderator plane)
   and moderation's NIP-98 dependency are real sibling gaps under the same "no NIP-98" rule but are
   outside this document's community/invite/channel/message/DM scope — flag to the team rather than
   silently carrying pubkey/NIP-98 forward in those two areas while everything else migrates.

**Single biggest risk to call out to the user**: this is materially larger than "finish the invite

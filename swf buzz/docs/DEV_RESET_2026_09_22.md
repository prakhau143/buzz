# Clean development reset and operator re-bootstrap — 2026-09-22

Local development only. **This document contains public identifiers only** — no
`nsec`, no private hex, no `ncryptsec`, no backup passphrase.

## 1. Why

The configured operator public key was
`0f61e5e47ca8c4e22c64bab3a1163989a4e3a2d45d014e3d153f1c15b2320029`. Signing in
as that operator requires its **private** key, which is not available on this
machine. Pasting the *public* key into the import field did not fail, because a
64-character hex value is a private key by definition and a Nostr public key is
also 64 hex characters: the app parsed it as a secret scalar and derived a
different identity, `7e13d4f6938d2cd7355161d7c973c36dbcf8fd8924201d146cb27d99a9c15702`,
which is a community **member**. Hence operator probe 403 and the member UI.

A public key cannot yield its private key. The old operator identity was
therefore retired and a fresh one provisioned, rather than weakening
authentication (no public→private mapping, no hardcoded operator role — see
`DECISIONS.md` D14/D15).

**Documented constraint (§2 of the reset brief).** `communities` cannot stay at
0: the relay is a multi-tenant server that selects a tenant by HTTP `Host` and
fails closed on an unknown one, so on every boot it recreates four bare
host-binding rows (`localhost`, `127.0.0.1`, `localhost:3000`, `127.0.0.1:3000`)
with **no owner and no members**. They are infrastructure, not communities in
the product sense, and were not forced away.

Schema, migrations, relay implementation and application source were untouched.
